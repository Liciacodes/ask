# Ask

A command bar assistant. Today: the command bar, reminders created from it and saved in Postgres, and an agent in the bar: type a sentence no command matches, Ask it, and approve each action on a preview card.

## How to work here

- **Explain first.** Before building something important, explain the idea in plain words: what it is, why it's needed, how it works. Then build it.
- **One small step at a time.** Finish one step, check it works, then start the next. Don't bundle unrelated changes.
- **API keys only in `.env.local`.** Never in code, config, commits or chat. `.env*` is gitignored; keep it that way.
- **Database: Postgres on Neon, through Prisma** (`prisma/schema.prisma`). Never edit a migration that has run; add a new one. The real database only gets `prisma migrate deploy`. Anything that empties tables runs through `scripts/with-test-db.mjs`, which points it at `TEST_DATABASE_URL` and refuses if that is the real database.
- **Every visitor's reminders are their own.** `proxy.ts` gives each visitor a random id in an httpOnly cookie (on `/api/*` only, so the page stays static). Signing in with Google is optional (`lib/google.ts`, `lib/session.ts`, routes under `app/api/auth/`): it moves the browser's guest reminders to the account and sets a session cookie, whose token the `sessions` table keeps only as a SHA-256. Every route starts with `await ownerFrom(request)` from `lib/session.ts` (the signed-in user's id, else the visitor's), refusing with `noVisitor()` when it's null. Every query filters by that id. A new route that reads or changes reminders must do the same. API tests act as `TEST_VISITOR` (`tests/api/helpers.ts`).
- **Tests never reach the real Google.** Every test run gets `FAKE_GOOGLE_ENV` (`scripts/fake-google.mjs`): fake credentials and endpoints, set by `scripts/with-test-db.mjs` and `playwright.config.ts`. `endpoints()` in `lib/google.ts` refuses Google's real URLs inside Vitest or with `ASK_FAKE_GOOGLE=1`. The sign-in trip is tested in `tests/api/auth.test.ts` against the fake; browser tests fake `/api/auth/me` (`fakeMe`). The ID token isn't signature-checked (it comes straight from Google's token endpoint), but `aud`, `iss`, `exp` and `email_verified` are, and a sign-in failing any of them is refused.
- **Privacy and terms.** `/privacy` and `/terms` (`app/privacy`, `app/terms`, `components/legal-page.tsx`) are static pages, linked from every page's footer (`components/site-footer.tsx`, which also holds the owner's name and contact). They say what Ask keeps, who else handles it (Vercel, Neon, Groq, Google), and that an account is deleted within 30 days of an email request. Anything that changes what Ask stores, or who it sends data to, must update the privacy page and its date.
- **"Add to Google Calendar" is only a link.** A saved reminder (the edit view, and the AI's card once saved) links to Google Calendar's own new-event page, filled in by `calendarLink` (`lib/calendar-link.ts`), and the person saves it there. Ask asks for no Calendar scope and stores nothing, so it works for guests too. `goHome` blocks `calendar.google.com` in every browser test: tests read the link and never follow it.
- **The agent never acts without an OK.** Every tool that changes something has an approval in `toolApproval` (`lib/agent/agent.ts`), and only read-only tools skip it. There is no permanent delete for the agent; cancel can be undone. Answering a card makes no model call. The server runs the action, `prepareStep` hands the next step to a stand-in that says nothing (`noReply`), and the bar writes its own line, like "Saved: Message Ak, Tuesday 24 Nov, 7:00 PM". The model hears of the answer with the next question, including why the server turned an action down (`convertDataPart`).
- **Reasoning never reaches the bar.** Groq sends gpt-oss's reasoning apart from its words, and the agent drops it (`sendReasoning: false`). If reasoning leaks into the words, everything up to gpt-oss's switch to its answer is cut (`withoutLeakedReasoning` in `lib/agent/reply-text.ts`). Tests use `thinksThenSays` in `tests/api/fake-model.ts`.
- **Every model call counts against a daily limit.** The agent route wraps the model in `countedModel` (`lib/agent/limits.ts`), which takes one of the site's calls for the day before each call to Groq. A new question first takes one of the visitor's questions (`takeQuestion`); answering a preview card isn't a new question. The limits are `ASK_VISITOR_QUESTIONS_PER_DAY` and `ASK_SITE_GROQ_CALLS_PER_DAY` (10 and 60 when empty), counted per UTC day in `daily_usage`. Anything new that calls a model must go through `countedModel`. What the bar says when a reply stops for lack of room is in `lib/agent/problems.ts`, shared by the server and the bar. Nobody waits long on Groq. The SDK doesn't retry (`maxRetries: 0`), and `waitsBriefly` (`lib/agent/limits.ts`) waits once, for at most 5 seconds; a longer wait shows the busy message straight away.
- **Real model calls only when the user says so.** Tests use a fake model (`MockLanguageModelV4` from `ai/test`) and never reach Groq, and code enforces it:
  - Every test run except `npm run test:live` gets an empty `GROQ_API_KEY`. `scripts/with-test-db.mjs` does it for Vitest, `playwright.config.ts` for the server Playwright starts.
  - `agentModel()` refuses an empty key. Inside Vitest it also refuses unless `ALLOW_REAL_GROQ=1`.
  - The browser tests run on a server of their own, never your dev server, and block any `/api/agent` call they don't fake.
  - No check ever sends a request to the user's dev server on port 3000: no browser, `curl`, script or test, even with every route faked. It has the real Groq key and the dev branch database. A faked `/api/agent` that threw once let a request through to it. To look at the app, use `npm run check:server`: a production build on port 3200, run through `scripts/with-test-db.mjs`, so its `GROQ_API_KEY` is empty and its database is the test database. Don't start your own server another way. In PowerShell, `$env:GROQ_API_KEY = ""` deletes the variable, and Next then loads the real key from `.env.local`.
  - `npm run test:live` refuses unless `ALLOW_REAL_GROQ=1` is set in the shell for that one command. The setting in `.env.local` is ignored.
  - `tests/no-real-groq.test.ts` tries these for real. Don't weaken any of them.
- **`lib/agent-actions.ts` (the tools' zod schemas) is the user's.** Review it and point out problems; don't edit it.
- **Commit messages describe the change.** Never "Day N" or other progress counters.

## Stack

- Next.js 16 (App Router), TypeScript, Tailwind CSS 4. See AGENTS.md: read `node_modules/next/dist/docs/` before writing Next.js code.
- UI SDK (`@ui-sdk/react`, `@ui-sdk/core`), in beta and pinned to an exact version. Before using it, follow the `ui-sdk` skill (`.claude/skills/ui-sdk`) and read `node_modules/@ui-sdk/react/docs/llms.txt`. For our own primitives, search `docs/core.md` by heading and read `docs/rendering.md`.
- Build UI from UI SDK **behaviors** in `@ui-sdk/core` (`definePrimitive`, `createPopup`, `createListbox`, …), not from ready-made component libraries.
- The week's cards move to another day by drag or keyboard. The primitive is `components/week/primitive.ts`, built on `createTransfer`, with one tab stop (`createRovingFocus`, `spatialMove`). The rules are `canMoveTo` and `movedDueAt` (`components/week/moves.ts`). A move shows at once and goes back if the server refuses (`move` in `components/week/use-week.ts`). Each day's cards are a `listbox` and each card an `option`, so browser tests find cards with `getByRole("option")` inside a day.
- AI: Vercel AI SDK 7 (`ai`, `@ai-sdk/groq`, `@ai-sdk/react`), pinned to exact versions. The bar's `useChat` settings live in `lib/agent/client.ts`, shared with the API tests, and the browser tests fake `/api/agent` with `e2e/fake-agent.ts`, in the route's own stream format. Read `node_modules/ai/docs/` before writing AI SDK code: APIs have changed (`toolApproval`, `isStepCount`, `instructions`). The model is Groq's `openai/gpt-oss-120b`, set in `lib/agent/model.ts`, the one line to change to swap providers. It reads `GROQ_API_KEY`, on the server only. The model works in local dates and times; the server converts them (`lib/time.ts`) and checks every action with the API's own schemas (`lib/agent/plans.ts`). "Next" plus a weekday can mean either of two weeks. When the latest message says it without a date, the server turns any action the model proposes into a question naming both dates (`lib/agent/which-week.ts`). Models also name the wrong weekday for a date, so the server changes any weekday the reply puts next to a date to that date's own (`lib/agent/weekdays.ts`). Groq is sent each tool's types and descriptions but not the schemas' patterns and formats (`sendsLeanTools` in `lib/agent/agent.ts`); the AI SDK still checks every call against the full schemas. A message that's gibberish, off topic or too vague gets the read-only `didNotUnderstand` tool, which ends the reply in one call. When the latest message has a date or time (`mentionsWhen` in `lib/agent/mentions-when.ts`), the first `didNotUnderstand` in a reply fails instead, telling the model it's a reminder to set, and that a question back must say what the reminder would be for, and the model is asked again, once; that call counts against the site's day but isn't a new question. The bar then shows fixed examples (`lib/agent/not-understood.ts`) and puts the message back in the field to fix.

## Design rules

- Keyboard-first, fast, and beautiful. Not a generic AI dashboard.
- Visual direction: **Calm week** (`docs/design/calm-week.html`). A grey page, a white board with 32px corners and a soft shadow, near-black ink, grey for secondary words, and dark buttons (`--strong`, which dark mode turns light). Figtree: body text 500, emphasis and headings 600 to 700. The header has a calendar tile: today's month on red, today's date under it. Cards are white with a thin border and a soft shadow. Each kind of reminder has only a coloured dot before its title (`--health`, …), and its icon in grey at the card's end, so colour is never the only clue; call and message share cyan. Sent, Not sent and Not saved are pills. Today's date is a dark circle. The chosen row gets a soft grey tint, with no highlighter. Colour tokens live in `app/globals.css`, with a dark variant. Every word reads at 4.5:1 on what's behind it, measured in the browser by `e2e/contrast.spec.ts`, light and dark.
- The command bar opens and closes with **no animation**: people do it many times a day.
- All other motion follows Emil Kowalski's rules (the `emil-design-eng` skill).

## Commands

- `npm run dev`: start the app at http://localhost:3000
- `npm run lint`: ESLint
- `npm run typecheck`: generate Next route types, then `tsc --noEmit`
- `npm run db:migrate`: apply migrations to the real database (`DATABASE_URL`). `npm run db:migrate:test`: the same for the test database (`TEST_DATABASE_URL`)
- `npm run test:api`: Vitest tests in `tests/`, calling the API route handlers against the test database. Run `npm run db:migrate:test` first whenever a migration is added. From Windows, run it in PowerShell: Git Bash hands Node a lowercase drive letter and Vitest then loads twice
- `npm run test:live`: real Groq calls on the 42 sentences in `tests/agent-cases.ts` (`tests/live/`, at most 3 calls each, paced under Groq's per-minute tokens). All 42 take about 63 calls, half of Groq's free day, shared with the live site; `-- -t "<words>"` runs a few. Only when the user says so; never in CI. It needs `ALLOW_REAL_GROQ=1` for that one command. When the user agrees to a number of calls, set `ASK_LIVE_CALLS` to it for the same command: the run refuses any call past it before it reaches Groq (`ASK_LIVE_CALLS=0` is a dry run showing which sentences a pattern picks). In PowerShell: `try { $env:ALLOW_REAL_GROQ = "1"; npm run test:live } finally { Remove-Item Env:ALLOW_REAL_GROQ }`. `npm run test:api` sends each case's expected answer through the server with a fake model
- `npm run check:server`: a production build at http://localhost:3200 for looking at the app, with an empty Groq key and the test database. Never look at the app on port 3000. It builds into `.next`; the browser tests build into `.next-e2e`, so neither replaces the other's build
- `npm run test:e2e`: Playwright browser tests in `e2e/` (Chromium). Each run builds the app into `.next-e2e` (`ASK_BUILD_DIR`, read by `next.config.ts`) and starts its own server on port 3100, beside your dev server, never reusing it. The build and the server run through `scripts/with-test-db.mjs`, so their database is the test database. First time: `npx playwright install chromium`

CI (`.github/workflows/ci.yml`) runs three jobs on every push: lint and typecheck; the API tests against a throwaway Postgres 18 container; and the browser tests against a production build, with a throwaway Postgres 18 of their own.
